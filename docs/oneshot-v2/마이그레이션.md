# 원샷 v2 마이그레이션 목록과 적용 순서

**개발용 DB에는 1~10번이 모두 적용돼 있다.** 1~9번은 원샷 v2 앞 바퀴에서 창구가 적용했고, 10번은 11-08 PM이 직접 `db push`했다. 11-09 00:25에 `supabase migration list`로 1~10번이 원격 이력에 모두 있음을 확인했다(`migration list`는 읽기만 한다). 이 빌드(코드 변경)는 마이그레이션을 새로 적용하지 않는다. 다른 DB(운영 등)에 적용할 때는 창구가 따로 한다. 모두 **더하기만** 한다(새 표·새 열·새 권한·새 트리거. 기존 열·데이터는 바꾸거나 지우지 않는다). 파일 이름의 시각 순서가 곧 적용 순서다.

**먼저 적용하고 나서 앱을 배포한다.** 앱이 새 열(`todos.position`)과 새 표를 바로 읽는다. 적용 전에 배포하면 할 일 목록 읽기가 실패한다.

**순서 · 파일 · 무엇을 더하나 · 앞 파일에 기대는 것**

2. `20261107100100_todo_notes.sql` · `todo_notes` 표(작업 기록), RLS, 개수 상한 트리거 · 1번의 고유 제약
3. `20261107100200_user_settings.sql` · `user_settings`(처음 설정·알림 설정), `category_ratios`(처음 정한 비율) 표, RLS · 기존 `categories (id, user_id)` 고유 제약
4. `20261107100300_evening_logs.sql` · `evening_logs` 표(저녁 기록, 쌓기만), RLS, 상한 트리거 · (없음)
5. `20261107100400_view_events.sql` · `view_events` 표(화면 본 것, 쌓기만), RLS, 상한 트리거 · (없음)
6. `20261107100500_focus_sessions.sql` · `focus_sessions` 표(타이머·먼저 한 기록), RLS, 상한 트리거 · 기존 `categories (id, user_id)`
7. `20261107100600_todo_offers.sql` · `todo_offers` 표(할 일 제시), RLS, 상한 트리거 · 기존 `categories (id, user_id)`
8. `20261107100700_weekly_goals.sql` · `weekly_goals` 표(이번 주 목표), RLS · (없음)
9. `20261107100800_push_subscriptions.sql` · `push_subscriptions` 표(푸시 구독), RLS, 상한 트리거 · (없음)
10. `20261107110000_ratio_other.sql` · **(고침 3바퀴)** `user_settings.ratio_other_percent` 열(처음 정한 비율의 기타 몫)과 그 열의 insert·update 권한 · 3번의 `user_settings` 표. **없어도 앱은 돈다**(열을 못 읽으면 기타 몫 없음으로 읽는다). 기타를 비율에 넣은 사용자의 저장만 이 파일이 있어야 한다. **개발용 DB에 적용함**(11-08 PM이 직접 `db push`. 23:05:33은 push한 시각이 아니라 `migration list`로 원격 이력에 10번이 있음을 확인한 시각이다. push 시각은 따로 기록하지 않았고 그 확인보다 앞이다). 되돌림 파일: `supabase/rollback/20261107110000_ratio_other.down.sql`

11. `20261109150000_category_ratio_history.sql` · **(고침 9바퀴, PM 「152 나」)** `category_ratio_history` 표(목표 비율이 바뀐 기록, 쌓기만), RLS(자기 행 select·insert만, update·delete 정책 없음), grant 명시(authenticated에 select와 `user_id`·`ratios` 열 insert만, anon 없음), 가벼운 check(배열·1~50칸·8KB), 한 사용자 행 수 상한 트리거(`private.category_ratio_history_enforce_limit`, 임시 1000, 넘으면 P0001 `category_ratio_history_limit`) · 기존 `private` 스키마(`20261104160723_create_todos.sql`). **없어도 앱은 돈다**(기록 쓰기만 실패하고 비율 저장은 성공, 로그만. 상한에 닿아도 같다). backfill 없음(다음 저장부터 쌓인다). **개발용 DB에 아직 적용하지 않음**(PM 승인 대기). 되돌림 파일: `supabase/rollback/20261109150000_category_ratio_history.down.sql`. 적용 뒤 `npm run test:rls`(`tests/integration/ratio-history-rls.test.ts`)

12. `20261117100000_goal_bundles.sql` · **(MO-46 목표 묶음 1단계)** `goal_bundles` 표(지난 목표 묶음만 쌓기, RLS 자기 행 select만, authenticated에 select grant만, insert·update·delete 없음), `user_settings`에 새 칸 넷(`bundle_started_at`·`restart_requested_at`·`bundle_revision`·`bundle_op_ids`, grant 없음), `categories.color_order`(보관 포함 만든 순서, 기존 행은 `created_at, id` 순서로 채움 — **기존 행을 바꾸는 유일한 곳**)와 새 행 색 순서 트리거, DB 함수 `save_goal_bundle`(한 트랜잭션: 충돌 검사·멱등·지난 묶음 남기기·분야 더하기/이름 바꾸기/보관/되살리기·비율 통째 바꾸기·목표 글·기타·비율 바뀐 기록)과 `set_restart_requested`(security definer, search_path 빈 값, execute는 authenticated만), 도우미 `private.doono_day`·`private.goal_bundle_ratios_sum`. 분야 이름 바꾸기·보관·되살리기는 이 함수로만 한다(`categories` update grant 없음) · 기존 `categories`·`user_settings`·`category_ratios`·`category_ratio_history`(없어도 함수는 돈다, 기록만 건너뜀)·`private` 스키마. **어느 DB에도 아직 적용하지 않음.** 적용 순서: **마이그레이션 먼저, 앱 다음**(앱이 새 칸을 읽는다). 되돌리기: `supabase/rollback/20261117100000_goal_bundles.down.sql`(**먼저 dump** — 지난 목표 기록이 사라진다. 돌린 뒤 `supabase migration repair --status reverted 20261117100000`). 적용 뒤 `supabase test db`(`supabase/tests/goal_bundles.test.sql`, 로컬 또는 개발 전용 DB)와 `npm run test:rls`(`tests/integration/goal-bundles-rls.test.ts`). 임시값(결정 필요): 지난 묶음 사용자당 1000행, 분야 목록 50칸, 함수 입력 16KB. 알려진 한계: `user_settings.goal_encrypted`·`ratio_other_percent`·`category_ratios`의 옛 열 단위 grant는 옛 앱이 쓰므로 그대로 둔다(앱 배포 뒤 거두기는 다음 일).

**고침 3바퀴 2부(기기 먼저 저장)에는 새 마이그레이션이 없다.** 쓰는 열이 모두 이미 있다(`client_started_at`·`client_saved_at`·`todos.day`·`todo_notes.day` 등). 위 10번은 1부의 기타 비율용이고, 없어도 앱은 돈다.

## 확인할 것
- **주의(권한 변경)**: 1번이 `todos`의 update 권한을 넓힌다. 기존 RLS 통합 시험 두 곳(`tests/integration/rls.test.ts`·`categories-rls.test.ts`)이 「update는 done만」을 단언하고 있어서 새 권한에 맞춰 바꿨다. 둘 다 DB가 없어 **돌려 보지 못했다**.
- 새 표의 RLS 시험은 `tests/integration/v2-rls.test.ts`에 있다(**미실행**). 적용 뒤 `npm run test:rls`로 돈다. 쌓기만 하는 표라 시험 행이 남는다(그 파일 머리의 SQL로 지운다).
- 개수 상한 값(분야 50, 작업 기록 20000, 저녁 기록 20000, 본 것 100000, 타이머 50000, 제시 50000, 푸시 구독 20, 목표 비율 바뀐 기록 1000)은 모두 임시다.
- 알림을 실제로 보내려면 마이그레이션 말고도 **서버 설정**이 필요하다(푸시 서명 키·서버 키·예약 비밀·예약 실행). `docs/oneshot-v2/임시값.md` ⑦ 참고.
- 11번 되돌림 파일 `supabase/rollback/20261109150000_category_ratio_history.down.sql`은 표(트리거 포함)와 기록, 상한 함수를 지운다(기록은 되살릴 수 없음). 앱 코드를 먼저 뺄 필요는 없다(표가 없으면 기록만 빠진다). 돌린 뒤 `supabase migration repair --status reverted 20261109150000`.
- 되돌림 파일(down)은 10번·11번만 있다: `supabase/rollback/20261107110000_ratio_other.down.sql`. 10번을 되돌릴 때만 손으로 돌리고(`db push`는 이 폴더를 올리지 않는다), 돌리면 기타 몫 값이 사라지니 그 열을 쓰는 코드를 먼저 뺀다. 나머지는 되돌림 파일이 없다: 새 마이그레이션으로 되돌리고, 코드를 먼저 뺀다.
