# 원샷 v2 기록 장치(계측) — 무엇을 어디에 남기나

PRD 4절(검증)·8절(기록과 계측)이 첫 판부터 넣으라고 한 기록이다. 모두 **앱 DB 표**에 두고, 사용자는 자기 기록만 읽고 쓴다(RLS). 서버 로그·외부 분석 도구는 쓰지 않는다. 여러 사용자 것을 합쳐 볼 때는 **값만** 내보내고 할 일 글·작업 기록·목표 글(암호화한 열)은 섞지 않는다. 내보낼 곳과 담당은 정하지 않았다(PRD 13절 열림).

## 한눈에

**무엇 · 표 · 언제 남기나 · 어떤 값**
- 할 일 제시 · `todo_offers` · 「오늘 먼저 할 일」 카드를 건넬 때와 타이머 탭이 추천할 때 · 어느 자리(`surface` card/timer_tab)·분야(null은 기타)·할 일·두노 하루·서버 시각·넘긴 시각. 같은 날·자리·분야·할 일은 한 번만 남기고(`offer_key`), 분석에서는 날·자리별 첫 제시만 센다(아래 SQL)
- 먼저 하기(타이머 시작) · `focus_sessions` · 타이머를 시작하는 순간 한 행 · 제시 번호(`offer_id`, 있으면 건넨 것으로 켠 것)·어디서 켰나(`surface`)·할 일·분야·**이번 주 목표 기준 반대편 여부**(`opposite_by_goal`, 목표 없는 주는 null)·**처음 정한 비율 기준 반대편 여부**(`opposite_by_ratio`)·서버 시각·기기 시각·끝낸 시각·진행한 초
- 저녁 기록 · `evening_logs` · 저장할 때마다 한 행(쌓기만) · **저장 방식**(`save_mode` prefilled/edited/not_split)·**대상 날**(`target_day`)·**저장 시각**(`saved_at` 서버 / `client_saved_at` 기기)·총시간·분야별 시간
- 화면 본 것 · `view_events` · 상태보기·분야 페이지가 그려진 뒤 한 번 · 화면(`screen` growth/category)·**입구**(`entry` after_save = 저녁 기록 저장 직후의 한 줄을 눌러 열었다 / self = 그 밖에 스스로 열었다)·두노 하루·서버 시각
- 할 일·작업 기록 · `todos`·`todo_notes` · 적을 때 · 두노 하루·분야·끝냄 · 「할 일을 적는 날의 비율」「작업 기록을 쓰는 할 일의 비율」(PRD 7-2 보는 법)의 재료
- 처음 설정 · `user_settings`·`category_ratios` · 마칠 때 · 처음 설정을 마친 시각(`onboarding_done_at`)·처음 정한 비율·알림 시각

## 시각을 둘 다 남기는 까닭
기록 위조를 막으려고 시각은 **서버 시계**(DB `now()`)로 정한다(22 4-3). 오프라인 저장과 맞추려고 기기 시계(`client_started_at`·`client_saved_at`)와 할 일의 적은 때(`writtenAt`, 최근 72시간 안일 때만 그 때의 하루)는 따로 둔다(PRD 10절).

**기기 먼저 저장(고침 3바퀴)에서 달라진 것**: 모든 쓰기가 기기에 먼저 들어가고 서버에는 나중에 가므로, 서버가 받은 때와 사용자가 누른 때가 다를 수 있다. 그래서 **하루 경계(서울 새벽 4시)는 누른 때(기기 시계, `clientAt`)로 기기에서 정해 함께 보낸다.** 서버는 그 때가 최근 72시간·미래 5분 안일 때만 따르고 밖이면 서버 시계의 하루를 쓴다. 이 규칙이 닿는 기록: 할 일·작업 기록의 날(`day`), 어제 것 가져오기의 「오늘」, 저녁 기록의 「오늘」(대상 날 범위 검사), 화면 본 것의 날(`view_events.day`), 이번 주 목표의 주(`week_start`), 먼저 한 기록의 날(`focus_sessions.day`). `saved_at`·`started_at`·`offered_at`·`viewed_at`은 여전히 서버가 정한다(서버에 올라간 때). **타이머만 예외**: 시작 시각은 기기가 보낸 `client_started_at`이 서버가 받은 때의 72시간 안·5분 뒤까지면 그것을 시작으로 읽고, 끝내기는 기기가 끝낸 때로 진행한 시간(`elapsed_seconds`)과 `ended_at`을 정한다(정한 길이 30분 상한). 그만큼 기록 위조 막기가 느슨해졌다.

## 검증 가설을 재는 SQL 보기(실행하지 않았다. 창구가 DB에서 돌려 보는 용도)

### 먼저 하기 비율(한 사용자의 한 주)
세로 값 = 그 주에 먼저 하기를 누른 비율 = 누른 횟수 ÷ 할 일을 제시한 횟수. 분자를 어떻게 셀지(넓게/제시한 것만)는 PRD 7-6·13절이 열어 두었다. 둘 다 셀 수 있게 기록해 두었다.

**제시는 다 남기고, 분석은 「날·자리별 첫 제시」로 센다**(PM 확정, 고침 3바퀴 d-69 ⑥). `todo_offers`에는 건넬 분야나 할 일이 바뀔 때마다 새 제시 행이 남지만(`offer_key`가 다르면 새 행), 분모는 같은 사용자의 같은 날·같은 자리(`surface`)에서 가장 먼저 건넨 것 하나만 센다. 아래 SQL의 `offers`가 그 값이다. 모든 제시 행 수가 필요하면 `offers_all`을 본다.

```sql
-- 주(월요일)별·사용자별: 제시 횟수(분모 = 날·자리별 첫 제시), 모든 제시 행 수, 시작 횟수(넓게), 건넨 것으로 시작한 횟수(좁게)
with first_offers as (
  select distinct on (user_id, day, surface) user_id, day, surface
  from public.todo_offers
  order by user_id, day, surface, offered_at, id
), weeks as (
  select user_id, date_trunc('week', day::timestamp)::date as week_start,
         count(*) as offers
  from first_offers group by 1, 2
), all_offers as (
  select user_id, date_trunc('week', day::timestamp)::date as week_start,
         count(*) as offers_all
  from public.todo_offers group by 1, 2
), starts as (
  select user_id, date_trunc('week', day::timestamp)::date as week_start,
         count(*) as starts_all,
         count(*) filter (where offer_id is not null) as starts_from_offer
  from public.focus_sessions group by 1, 2
)
select coalesce(w.user_id, s.user_id) as user_id, coalesce(w.week_start, s.week_start) as week_start,
       coalesce(w.offers, 0) as offers, coalesce(a.offers_all, 0) as offers_all,
       coalesce(s.starts_all, 0) as starts_all, coalesce(s.starts_from_offer, 0) as starts_from_offer
from weeks w
full join starts s on s.user_id = w.user_id and s.week_start = w.week_start
left join all_offers a on a.user_id = coalesce(w.user_id, s.user_id) and a.week_start = coalesce(w.week_start, s.week_start)
order by 1, 2;
```

### 가로 값(저녁 기록 날 수)
```sql
-- 그 주까지 쌓은 저녁 기록 날 수(누적)와 그 주에 저녁 기록을 한 날 수. 저장 방식별 날 수도 함께(세는 법은 나중에: G9)
select user_id, date_trunc('week', target_day::timestamp)::date as week_start,
       count(distinct target_day) as days_this_week,
       count(distinct target_day) filter (where save_mode = 'not_split') as days_not_split
from public.evening_logs group by 1, 2 order by 1, 2;
```

### 성장 화면(상태보기)을 본 횟수(입구별)
```sql
select user_id, date_trunc('week', day::timestamp)::date as week_start, entry, count(*) as views
from public.view_events where screen = 'growth' group by 1, 2, 3 order by 1, 2, 3;
```

### 이번 주 목표를 세운 주(집중 기간) 나눠 보기
```sql
select g.user_id, g.week_start, true as focus_week from public.weekly_goals g;
```

## 알아 둘 한계(22·23이 짚은 것)
- 이번 판의 「늘어난 역량」은 분야에 쓴 시간이다. 결과를 「역량이 늘었다」로 읽으면 안 된다(PRD 5절 G5).
- 타이머 시간이 저녁 기록을 미리 채우므로 저녁 기록 날 수가 먼저 하기의 결과일 수 있다(PRD 4절 한계).
- 확인하는 사람이 PM 한 명인 동안은 검증이 약하다(PRD 11절).
- 「봤다」는 화면이 그려진 때다. 머문 시간·끝까지 봄은 재지 않는다(PRD 8절 열림).
