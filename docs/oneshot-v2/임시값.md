# 원샷 v2 임시값 목록

원샷 v2 빌드(2026-11-07)에서 PRD의 열린 질문·정하지 않은 값을 만나, 가장 단순하고 되돌리기 쉬운 쪽을 **임시값**으로 정한 것이다. 이 파일이 다음 고침 바퀴의 입력이다.
한 줄 꼴: **무엇 · 고른 값 · 이유 · PRD 어디**. 코드에서는 「임시」 주석이나 `lib/app-config.ts` 한 곳에서 바꾼다.

**줄 수: 160줄**(아래 절들의 「- 」 줄. 절 이름은 만든 순서를 따름: 0 → 0-1 → ① → ② → ③ → ④ → ⑤ → ⑥ → ⑦ → 오프라인 → 기기 먼저 저장(고침 3바퀴) → 기기 먼저 저장: 알려진 한계(고침 4바퀴) → AI 자리 → 고침 1바퀴 → DB 검토. 고침 3바퀴에서 PM 답(d-69)으로 바뀐 줄은 그 자리에서 고치고 「고침 3바퀴」라고 적었다). 같이 보는 문서: `기록-장치.md`(무엇을 어디에 남기나), `마이그레이션.md`(적용 순서).

**다음 고침 바퀴에서 가장 중요한 다섯**
1. **알림은 바깥 설정이 있어야 실제로 간다**(⑦): 푸시 서명 키 셋(`NEXT_PUBLIC_VAPID_PUBLIC_KEY`·`VAPID_PRIVATE_KEY`·`VAPID_SUBJECT`)·서버 키(`SUPABASE_SERVICE_ROLE_KEY`)·예약 비밀(`CRON_SECRET`)·15분 간격 예약이 없으면 알림은 켜지지 않는다. 푸시 본문 암호화는 새 패키지가 필요할 수 있어 본문 없는 신호만 보내고, **알림 종류·글·주소는 신호를 받은 서비스 워커가 서버에 물어 받는다**(고침 3바퀴). 실제로 보내지는지 시험하지 못했다
2. **기기 먼저 저장 구조**(「기기 먼저 저장」 절): 모든 쓰기가 기기 거울에 먼저 들어가고 보낼 줄이 서버에 뒤에서 보낸다. 맞추기 규칙은 「보낼 줄에 남은 것은 기기가 이김」(서버에 updated_at 열이 없어 마이그레이션 없이 한 근사), 타이머 진행 시간은 기기 시각을 믿는 범위가 72시간이라 기록 위조 막기가 느슨해짐. **실기기·두 기기·IndexedDB 용량·끊긴 채 새로 열기는 보지 못했다**
3. **먼저 하기를 재는 규칙**(⑤·④): 「제시한 횟수」(같은 날·자리·분야·할 일은 한 번), 분자(넓게 셈), 저녁에도 타이머 탭이 추천하는 것, 급한 때를 가르지 않는 것은 모두 임시다. v8 가설의 값이 이 규칙에 달렸다
4. **부족(채울 시간)과 반대편 계산**(③·④): **기타는 처음 정한 비율에 넣었을 때만 든다**(PM d-69, 새 마이그레이션 `ratio_other` 적용 전에는 기타를 쓰는 사용자의 저장이 거절됨). 처음 정한 비율 기준은 이번 주 안에서만, 목표를 세운 주는 목표 기준(PM 확정)
5. **할 일 update 권한을 넓힌 것과 DB 시험**(0): 1번 마이그레이션이 `todos`의 고칠 수 있는 열을 넓혀 기존 RLS 통합 시험 두 곳을 바꿨고, 새 표 RLS 시험(`v2-rls.test.ts`)과 함께 **DB가 없어 한 번도 돌리지 못했다**. 적용 뒤 `npm run test:rls`부터 돌릴 것

- 서버가 계속 하는 것 · 로그인, 암호화(할 일 글·분야 이름·목표·작업 기록), 푸시 구독·전송, 예약 실행, **먼저 할 일 제시를 정함**(기록 위조 막기 22 4-3), 모든 쓰기를 다시 검사, 분야 페이지(여러 날 모음) 읽기
- 맞추기 규칙 · **보낼 줄에 남은 쓰기는 기기 것이 이기고, 나머지는 서버 것이 이긴다**(서버 사본 위에 보낼 줄을 다시 입힌다). PM이 말한 「행마다 나중에 고친 쪽이 이김(updated_at)」은 서버에 그 열이 없어 마이그레이션 없이 「서버에 보낸 순서(기기 시각 순)」로 근사했다. 두 기기가 같은 행을 끊긴 채 고치면 나중에 서버에 닿은 쪽이 이긴다 [미검증] · 임시
- 서버가 거절한 쓰기 · 보낼 줄에서 빼고 거울을 다시 입혀 기기 것을 되돌리고, 화면 맨 위에 한 줄 「서버가 받지 않은 기록 n개를 되돌렸어요」(닫기)를 보인다. **고침 4바퀴**: 글이 있는 쓰기(할 일·고친 할 일·작업 기록·분야·목표 한 문장·저녁 기록)는 내용을 이 사용자 기기 저장소(`rej/<사용자>/`)에 보관해 화면에서 보고 「복사」할 수 있다(다시 적기는 사용자가 붙여 넣어 한다, 자동 재전송 없음). 일시 오류(unavailable·config)로는 버리지 않는다: 옛 값 「6번이면 거절」 · 임시
- 서버에 닿지 못할 때·일시 오류 · 줄을 멈추고 2초에서 60초까지 두 배씩 기다려 다시 보낸다(끊김은 횟수에 안 센다. 일시 오류는 세어 6번(`STALLED_AFTER_ATTEMPTS`, 약 1분)을 넘으면 화면에 「n개 기록을 아직 보내지 못했어요. 계속 보내고 있어요」, 고침 4바퀴). 연결이 돌아오거나 화면이 다시 보이면 바로 다시. 로그인이 풀렸으면 멈추고 「다시 로그인해 주세요」를 알린다(줄은 지우지 않아 다시 로그인하면 이어서 보낸다)
- 보내는 방법 · 줄의 앞에서 하나씩 Server Action으로. **같은 쓰기를 다시 보내도 한 번만 들어간다**: 적기·분야 더하기·작업 기록·저녁 기록·타이머 시작·본 것은 화면이 만든 id, 끝냄·고치기·순서·설정·목표는 값을 정하는 것이라 같은 결과, 지우기는 「없음」도 성공으로 본다. 여러 탭은 Web Locks로 한 탭만 보낸다(잠금 이름은 사용자와 상관없이 `duno-flush` 하나, 고침 4바퀴). 보낸 탭은 「보냈다는 표시(비석, `sent/<사용자>/<줄 열쇠>`, 하루 뒤 지움)」를 남기고, 다른 탭은 저장소에 줄 칸이 없고 이 표시가 있을 때만 건너뛴다. 표시가 없거나 저장소 읽기가 실패하면 보낸다(옛 값: 저장소에 없으면 건너뜀 — 지워진 것·읽기 실패를 「보냈음」으로 오해했다) · 임시
- 하루 경계(새벽 4시·서울) · **쓰기를 누른 때(기기 시계)로 기기에서 정해** 함께 보낸다(`clientAt`). 서버는 최근 72시간·미래 5분 범위만 검사하고 밖이면 서버 시계를 따른다. 작업 기록 날·가져오기의 「오늘」·저녁 기록의 「오늘」·본 것의 날·목표의 주·타이머의 하루에 쓴다(기존 할 일 적기의 `writtenAt` 규칙을 넓힘) · PM 요청
- 타이머 · 시작 시각은 기기가 보낸 시각(`client_started_at`)이 서버가 받은 때의 72시간 안·5분 뒤까지면 그것을 시작으로 본다(`started_at`은 서버 기본값이라 못 바꾼다). 끝내기는 기기가 끝낸 때로 진행한 시간을 정한다(시작 이후·범위 안일 때, 정한 길이 30분 상한). **기록 위조 막기(22 4-3)가 느슨해졌다**: 기기 시계를 믿는 범위가 72시간이라 사용자가 기기 시계로 진행한 시간(최대 30분)을 정할 수 있다. 반대편 여부 둘은 서버가 올라오는 때의 이번 주 기록으로 정한다(끊긴 채 켠 타이머는 시작 때가 아니라 올라가는 때 기준) · 임시
- 먼저 할 일 제시 · 건넬 분야·할 일·시각은 서버만 정한다. 기기는 오늘 받은 제시를 거울에 두고 먼저 보여 준 뒤 뒤에서 서버에 다시 묻는다(바뀌면 거울이 바뀌어 화면이 따라간다). 이 기기에 제시가 없을 때(처음)는 서버를 기다리고, 끊겨 있으면 건네지 못한다. 넘기기·타이머로 시작은 보낼 줄에 넣고 거울에서 바로 거둔다
- 본 것 기록·분야 페이지 · 본 것은 보낼 줄에 넣는다(`clientAt`으로 하루). 분야 페이지는 서버에서만 읽는다(여러 날 모음): 열어 본 적이 있으면 그것을 먼저 보이고 뒤에서 새로 받아 둔다. 방금 적은 것은 서버에 올라가기 전에는 분야 페이지에 안 보인다 · 임시
- 첫 화면 · 서버는 로그인한 사용자 번호만 넘기고 **다시 여는 기기에는 개인 데이터를 HTML에 싣지 않는다**(예전에는 서버가 DB를 읽어 HTML에 싣느라 그만큼 늦었다). 기기에 거울이 있으면 서버를 기다리지 않고 바로 그린다. 「이 기기에 거울이 있다」는 표시는 쿠키 하나(`duno-device`, 값은 사용자 번호, 로그아웃 때 지움)다. **이 기기에서 처음 여는 사용자**(로그인 직후 포함, 표시 없음)에게는 서버가 서버 사본을 HTML과 함께 실어 보내 JS를 받은 뒤 서버에 다시 받으러 가는 왕복을 없앴고, 사본을 못 실었으면 서버 사본이 올 때까지(8초 상한) 「불러오는 중」, 못 받으면 읽기 실패 안내(비어 있는 것으로 보이지 않게). **알려진 값**: 목록은 JS가 기기 저장소를 읽은 뒤에 그려져 예전(HTML에 목록)보다 빠른 망 +20~30ms·느린 망 +80~90ms, 느린 망 첫 방문은 +1.4초 늦게 보인다(보고서 10절) · 임시
- 로그아웃 · 먼저 보낼 줄을 서버에 보내 본다(6초 상한). 못 보낸 기록이 있으면 「보내지 못한 기록이 있어요. 지금 로그아웃하면 이 기록은 사라져요.」를 알리고 사용자가 「로그아웃」이나 「취소」를 고른다. 로그아웃하면 이 사용자의 기기 저장소(거울·보낼 줄·고른 값·보냈다는 표시·받지 않은 글 보관)를 지운다. **고침 4바퀴**: 못 보낸 기록은 이 탭 줄이 아니라 기기 저장소의 `op/<사용자>/` 수로 세고(다른 탭의 줄 포함), 보내 볼 때 다른 탭의 줄도 함께 보낸다. 지우기는 돌던 보내기·고른 값 쓰기를 1.5초(`WIPE_WAIT_MS`)까지만 기다리고, 그 뒤 늦게 온 응답은 기기에 적지 않는다. 같은 출처의 다른 탭에는 BroadcastChannel(`duno-local`)로 알려 그 탭도 자기 것을 지우고 멈춘다(안내 「다른 탭에서 로그아웃했어요」·「다시 열기」) · PM 요청
- 다른 계정 · 기기 저장소 열쇠가 사용자 번호별이고, 로그인 직후 이 기기에 남은 다른 사용자 것을 모두 지운다. **고침 4바퀴(S1)**: 보낼 줄의 쓰기는 서버 입구 하나(`app/local/actions.ts`의 `sendLocalOp`)로 「이 줄의 주인」(기대 사용자 번호)을 싣고, GET /mirror는 `x-duno-expected-user` 머리글을 싣는다. 서버는 세션 사용자와 다르면 `account_mismatch`로 거절한다(기대 번호는 거절에만 쓰고 권한을 넓히지 않는다: 쓰기는 기존 Action이 세션 사용자로). 사본에는 주인(`userId`)을 싣고 기기도 다르면 받지 않는다. 거절을 받은 탭은 보내기를 멈추고 자기 사용자 것을 지운 뒤 다시 연다. 다른 사용자가 다른 탭에서 열리면(BroadcastChannel 「active」) 이 탭도 지운다. 옛 판 오프라인 보관함(localStorage)에 남은 글은 첫 실행 때 보낼 줄로 옮기고(적은 때 그대로) 지운다 · 검토 A6의 연장
- 끄는 법 · 서버 설정 `DUNO_LOCAL_FIRST=off`를 두면 예전 방식(서버가 읽어 넘기고 화면이 서버에 직접 쓴다)으로 돈다. 문제가 생겼을 때의 안전 장치이고, 같은 빌드에서 전·후 반응 속도를 견주는 데도 썼다 · 임시
- 기기에 둘 수 있는 양 · 거울은 JSON 하나(할 일 8일·저녁 기록 전체·타이머 8일), 보낼 줄은 한 쓰기당 한 항목. 저장소가 가득 차거나 막히면 메모리로 돌고 새로고침하면 사라진다 [미검증]
- 분야 이름 겹침(고침 4바퀴, F4) · 끊긴 채 만든 분야가 서버에서 duplicate(같은 이름이 이미 있음)면, 서버가 돌려준 그 분야(번호·이름)를 거울에 넣고 뒤의 보낼 줄(할 일·저녁 기록·이번 주 목표·비율·타이머)의 분야 번호를 그 번호로 바꿔(같은 분야가 둘이 되면 분·퍼센트를 더함) 저장소에도 다시 적고 보낸다 · 임시
- 이번에 하지 않은 것 · 새 마이그레이션(2부에는 없음: 쓰는 열이 모두 이미 있다), 서버 쪽 행마다 updated_at 비교, 끊긴 채 앱을 새로 여는 것(위 오프라인 절), 분야 페이지·작업 기록 처음 열기를 기기에서 계산하는 것, 서버가 쓰는 시각을 기기 시각으로 바꾸는 열(`started_at` 등)

- S3 세션 만료(로그아웃 아님) · 기기 저장소를 그대로 둔다(못 보낸 줄을 지키려는 설계). 함께 쓰는 기기에서는 평문이 남는다. 그 뒤 다른 사용자가 로그인하면 그 탭이 「active」를 알리고 로그인 직후 지우기가 돌아 지워진다 · 알려진 한계
- L1 건너뛴 줄의 순번 · 다른 탭이 보낸 것을 건너뛸 때(비석이 있을 때) 순번(ackSeq)을 올리지 않아, 그 사이 받은 낡은 사본이 그 항목을 잠깐 가릴 수 있다. 다음 받기에서 맞는다(고침 4바퀴에서 건너뛰는 때가 「비석이 있을 때」로 좁아졌다) · 알려진 한계
- 결정 대기(팀장·PM) · 「다른 탭에서 로그아웃함」을 받은 탭은 자동으로 새로고침하지 않고 안내와 「다시 열기」만 보인다. 로그아웃한 탭이 서버 로그아웃을 마치기 전에 다시 열면 같은 세션으로 사본을 다시 받아 기기에 적기 때문이다. 「계정이 바뀜」(account_mismatch·다른 사용자가 열림)은 세션이 이미 새 사용자라 바로 새로고침한다 · 임시, 결정 필요

## 합치기에서 정한 것 (고침 4바퀴 합치기, 팀장 지시)
- 분야 색 · 다이얼(처음 정한 비율·저녁 나누기)과 상태보기(띠·원·분야 줄 막대·색점)가 같은 분야에 같은 색 변수를 쓴다. 분야 순서의 기준 = 보관하지 않고 이름을 읽을 수 있는 내 분야를 만든 순서(created_at 오름차순, 같으면 id)에서의 자리(0부터). 세 화면이 받는 분야 목록이 모두 이 순서다. 처음 설정은 고르지 않은 분야도 자리를 차지한다(`RatioEntry.colorOrder`). 기타는 늘 기타 색 · 임시, 디자인 확정 뒤 · `tests/unit/category-color-link.test.tsx`
- 분야 색 자리값 아홉 개 · 서로 달라야 하고(기타는 막대 바탕 `--color-skeleton`과도 달라야 한다) 지금 있는 색 토큰의 값 중에서만 고른다. 있는 값이 열 개뿐이라 번호 4를 `#FFFFFF`로 바꿔 아홉 개를 서로 다르게 만들었다. 그 결과 번호 4·6·7·8은 바탕과 비슷하게 옅어 막대에서 잘 안 보일 수 있다 — 자리값이라 디자인 확정 뒤 값만 바꾼다 · 임시
- 0% 분야는 저장 목록에서 뺀다 · `entriesToRatios`가 0% 줄(분야·기타)을 싣지 않는다. 분야 50개 + 기타 몫이어도 51항목이 되어 상한 50에 거절되는 일이 없다. 저장 목록에 없는 분야는 상태보기·놓친 분야·채울 시간·다시 열 때 모두 0%로 읽고, 서버 저장은 목록에 없는 분야의 옛 비율 행을 지운다. **남은 구멍**: 분야 50개가 모두 1% 이상이고 기타도 1% 이상이면 51항목이라 여전히 거절된다(서버 검증은 바꾸지 않았다) · 결정 대기

## 알려진 한계 (고침 4바퀴 합치기 고침1, 전체 검토 R1)
- 처음 정한 비율 서버 저장에 트랜잭션이 없다 · `saveRatiosForUser`(`lib/settings/core.ts`)가 upsert → 조회 → 삭제를 따로 보낸다. 0% 분야를 저장에서 뺀 뒤에는, 두 탭·두 기기가 동시에 저장하면 0%로 줄인 분야의 옛 몫이 남을 수 있다. 읽을 때 합으로 나눠 읽어 피해는 작고 재현은 못 했다 · 임시, 알려진 한계
- 안전 장치 `DUNO_LOCAL_FIRST=off`에서는 고른 상태보기 보기(띠·원·막대)가 기억되지 않는다. 기억은 기기 저장소(`lib/local`)에 있어서 기기 먼저 저장이 꺼져 있으면 쓸 곳이 없다 · 임시, 알려진 한계
- 처음 설정은 「이미 있는 분야」를 catalog 끝에 붙인다 · 다른 기기에서 만든 분야는 catalog 끝에 붙어 그 분야의 색이 잠시 다를 수 있다(분야 색은 catalog 자리를 따른다). 처음 설정을 다시 열면 만든 순서로 맞는다 · 임시, 알려진 한계
